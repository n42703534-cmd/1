# 共享设施到达负荷预判版论文框架

参考论文：Wei et al., "Dynamic firefighting route planning for efficient evacuation in complex subway stations: A deep learning-enhanced robust optimization approach", *Simulation Modelling Practice and Theory*, 146, 103223, 2026.

本版状态：已被第 12 版替代。第 11 版仍然把论文问题写成“路径分配策略如何识别未来负荷”，这本质上还是算法/模型问题，而不是大型复杂地铁站应急疏散现场本身的问题。后续正式框架以 `12_station_evacuation_problem_framework_cn.md` 为准。

## 1. 先把问题说成人能立刻理解的话

参考论文的问题很清楚：

> 消防预设路线在动态火灾环境与疏散干扰下可能失效。

本文也必须有同等清楚的问题。建议不要再用“当前路径组织看不见到达时刻瓶颈”作为主表述，它太抽象。更好的表述是：

> 在高负荷多线换乘站疏散中，若路径分配只依据当前距离或当前拥挤状态，多个客流批次可能被连续导向同一楼扶梯、闸机、通道或出口。虽然该设施在决策时尚未显著拥挤，但已被分配到该设施的后续到达客流可能超过其服务能力，从而在乘客真正抵达时形成排队和滞留。本文关注的不是“找一条更短路径”，而是如何在排队显性发生之前识别共享设施的未来到达负荷超载，并据此组织疏散路径。

因此，本文的核心问题应定义为：

**共享设施到达负荷超载的滞后识别问题。**

这比“到达时刻瓶颈不可见”更具体，因为它同时说明了：

- 对象：楼扶梯、闸机、通道、出口等共享服务设施；
- 原因：多个客流批次的未来到达负荷超过设施服务能力；
- 失效机制：当前状态尚未拥挤，路径分配继续向同一设施集中；
- 后果：乘客到达后形成排队、滞留和尾部疏散延长；
- 解决方向：提前估计到达负荷与服务能力的差额，而不是只读当前密度。

## 2. 与参考论文的真正对应关系

不能只模仿参考论文的表面流程，应当模仿它的“问题变量化”方式。参考论文不是说“火灾环境很复杂”就结束，而是把复杂性落到可建模对象：通行时间预测、时间不确定性、消防价值、路线成本、火灾环境和乘客疏散结果。

本文也应把“路径分配失效”落到可计算对象：共享设施、到达负荷、服务能力、预测队列、路径分配和实际排队。

| 参考论文 | 本文应对应的写法 |
|---|---|
| 发现消防预设路线可能受烟气、温度、通道拥堵和疏散干扰而失效 | 发现基于当前状态的疏散路径分配可能因共享设施未来到达负荷超载而滞后失效 |
| 构建上层消防网络与下层乘客疏散网络的耦合关系 | 构建路径分配层与共享设施服务层的耦合关系 |
| 用 BKA-GRU 预测关键节点通行时间，为消防路线时间计算提供输入 | 预测乘客批次到达共享设施时的队列和等待时间，为路径分配提供输入 |
| 用鲁棒优化处理旅行时间和灭火时间不确定性 | 用承诺到达和服务能力投影处理“当前未拥挤但未来会排队”的时间滞后 |
| 用 Gurobi + IVYA 求解消防路线优化模型 | 用时间依赖路径分配求解在未来等待成本下的可行疏散路径 |
| 用 PyroSim + Pathfinder 和多指标评价证明消防策略有效 | 用低负荷控制、高负荷压力、敏感性和 Pathfinder 对照证明共享瓶颈超载被提前识别并缓解 |

这一版的关键不是说本文也有“预测、优化、验证”，而是要让读者看到：本文预测的不是泛泛的时间，优化的不是泛泛的最短路，验证的也不是泛泛的总时间，而是围绕“共享设施未来到达负荷是否超过服务能力”展开。

## 3. 新的核心技术路线

建议把技术路线改成：

```text
基于当前状态的路径分配在高负荷换乘站中会滞后识别共享设施超载
-> 将楼扶梯、闸机、通道和出口抽象为具有服务能力的共享资源
-> 计算“当前队列 + 已分配客流未来到达量 - 到达前可释放服务量”
-> 将预测等待时间纳入路径代价，进行时间依赖路径分配
-> 在同一服务能力约束下推进疏散过程，检验路径分配是否真实转化为排队减少
-> 用低负荷控制、高负荷压力、参数敏感性和 Pathfinder 对照验证有效性与边界
```

这个版本比第 10 版更清楚，因为每一步都有明确的研究作用。

## 4. 每一步为什么必须存在

### 4.1 为什么要构建“路径分配层—共享设施服务层”耦合模型

因为本文的问题不是图上两点之间的最短距离，而是多批次乘客对同一受限设施的服务能力竞争。如果只把站内空间建成普通路径图，楼扶梯、闸机、出口就只是边或节点，模型只能表达“经过这里的距离/时间”，不能表达“已经有多少尚未到达的客流承诺要使用它”。

因此，耦合模型的作用不是为了显得复杂，而是为了把路径选择的后果写入设施服务过程：

```text
某批乘客选择路径
-> 该路径上的楼扶梯/闸机/出口在未来某时刻收到一批到达负荷
-> 这些负荷占用服务能力
-> 后续批次选择路径时必须看见这部分未来占用
```

这对应参考论文中“消防网络与乘客疏散网络耦合”的思想。参考论文耦合是为了说明消防路线会影响乘客疏散环境；本文耦合是为了说明路径分配会改变共享设施未来排队状态。

### 4.2 为什么要预测队列和等待时间

因为本文要解决的失效点就是“当前状态滞后”。如果只看当前队列 \(Q_v(t)\)，一个设施可能看起来仍然可用；但若已经有大量客流被分配到该设施，并将在未来 \(\tau\) 时间内到达，则设施在目标批次到达时可能已经超载。

建议在论文中引入一个直观指标：

```text
到达负荷压力 = 当前队列 + 目标到达前已承诺到达量 - 目标到达前可释放服务量
```

若该值大于 0，说明即使当前设施不拥挤，目标批次到达时也会面对排队。这个指标可以作为“问题发现”的核心图表，而不是只说“瓶颈不可见”。

队列预测的研究意义是：

- 把未来排队从现象描述变成路径分配前可读取的变量；
- 区分“当前拥挤”和“即将拥挤”；
- 让路径组织在拥堵形成前改变分配，而不是拥堵形成后再补救。

### 4.3 为什么还需要时间依赖路径分配

这是第 10 版最没有讲清楚的地方。预测队列本身不能完成疏散组织，它只能告诉模型“某设施未来会排队”。论文还必须回答：知道未来会排队之后，乘客应该走哪条路？

时间依赖路径分配的作用就是把预测结果转化为实际路径决策。它不是为了证明 AA* 多好，而是因为路径代价随到达时间变化：

- 同一楼梯，早到可能无需等待，晚到可能需要排队；
- 同一出口，当前看起来空闲，若已有多批客流承诺到达，则后续批次成本升高；
- 同一路径，对不同出发批次的代价不同，不能用固定边权一次性表示。

因此，路径搜索的研究意义是：

```text
将“未来队列预测”转化为“可执行的客流分配方案”
```

如果没有这一步，论文只能停留在“我们能预测哪里会堵”，却不能说明如何把乘客分配到其他可行路径上。

正式稿中应避免写“搜索可行路径组织”这种含混表述，改为：

> 在预测等待成本随到达时刻变化的条件下，本文采用时间依赖路径分配方法，为不同客流批次选择综合通行时间和预测等待时间较低的可行疏散路径。

### 4.4 为什么要共享容量执行

共享容量执行不是为了“保持一致”这个空泛目标，而是为了防止模型在评价阶段把排队机制抹掉。

如果路径分配阶段考虑了楼扶梯、闸机和出口的服务能力，但仿真执行阶段允许乘客无限通过这些设施，那么模型可能在纸面上预测了排队，却在结果中看不到真实滞留；反过来，如果执行阶段的容量规则与预测阶段完全不同，读者也无法判断结果改善来自路径组织，还是来自仿真规则不一致。

因此，共享容量执行的研究意义是：

- 检验路径分配是否真正减少了服务设施排队，而不是只改变了路径名称；
- 保证多个客流批次竞争同一设施时，排队、释放和滞留按同一服务能力规则发生；
- 使“预测的到达负荷超载”能够在仿真中表现为可测量的队列时长、拥挤人时和尾部清空时间。

更清楚的表述应是：

> 本文在执行层使用与预测层一致的设施服务能力约束推进疏散过程，从而检验预测型路径分配是否能够在实际队列演化中减少关键设施滞留。

这一步对应参考论文中 PyroSim/Pathfinder 的作用：不是装饰，而是把模型决策放回具有物理/行为约束的场景中检验。

## 5. 低负荷、高负荷、敏感性和 Pathfinder 分别证明什么

第 10 版把这些实验并列写成“验证机制与效果”，确实太笼统。它们应当承担不同证据角色。

| 实验部分 | 它回答的问题 | 为什么能说明解决问题 |
|---|---|---|
| 低负荷场景 | 当需求未明显超过共享设施能力时，模型是否会过度干预？ | 如果低负荷下路径变化很小、效率不劣化、重路由不频繁，说明模型不会为了“预判瓶颈”制造不必要绕行 |
| 高负荷场景 | 当多线客流竞争同一设施时，模型能否提前分散未来到达负荷？ | 如果关键设施到达负荷压力、排队持续时间、拥挤人时或尾部疏散时间下降，说明模型确实缓解了本文定义的失效机制 |
| 机制分析 | 改善是否来自共享瓶颈预判，而不是偶然路径差异？ | 通过线路—出口分配、关键设施队列时序、承诺到达量变化，证明路径分配改变发生在原本将超载的设施上 |
| 敏感性分析 | 结论是否依赖某一个容量、密度阈值或重路由阈值？ | 若参数扰动下仍能维持主要趋势，说明结果不是单一参数调出来的；若失效，也能界定适用范围 |
| Pathfinder 对照 | 中观模型的拥堵区域和疏散趋势是否具有微观仿真一致性？ | 若 Pathfinder 中关键拥堵区域、出口使用趋势或尾部疏散变化方向一致，可以增强外部合理性；若不一致，则说明模型边界 |

低负荷不是漏掉，也不是主效果来源。它在论文中的角色类似“正常工况控制组”：高负荷是问题暴露场景，低负荷是不过度干预检验。正式稿可以这样写：

> 低负荷场景用于检验模型在共享设施服务能力未成为主导约束时是否保持路径组织稳定；高负荷场景用于检验模型在多源客流竞争共享设施时是否能够降低到达负荷超载和关键设施排队。

## 6. 结果章节应按证据链而不是按模式堆叠

参考论文的结果不是简单“模型 A 比模型 B 好”，而是先验证预测模型，再验证求解，再比较不同消防策略，再看火灾环境和乘客疏散结果。本文也应采用类似证据顺序。

建议结果章节改为：

### 6.1 基于当前状态路径分配的共享设施超载诊断

目的：证明本文问题存在。

应展示：

- 某些关键楼扶梯、闸机或出口在决策时当前队列不高；
- 但根据已分配客流的未来到达量与服务能力计算，到达负荷压力已经为正；
- 后续仿真中该设施确实出现排队持续、拥挤人时增加或尾部清空延迟。

如果没有这一节，后文所有方法都像“为了算法而算法”。

### 6.2 到达负荷预测与路径分配机制验证

目的：证明方法部件是对准问题的。

应展示：

- 加入承诺到达后，后续批次能读取前序批次对设施能力的占用；
- 当某设施预测等待上升时，路径分配会转向其他可行设施；
- 若去掉承诺到达或预测等待项，路径分配会重新集中到同一共享设施。

这比单纯写“小网络测试通过”更有说服力。

### 6.3 低负荷场景：稳定性与不过度干预

目的：证明方法在问题不强烈时不会乱改路径。

应展示：

- 总疏散时间与基线接近或不劣化；
- 重路由次数受控；
- 关键设施队列不被人为转移成新的拥堵；
- 出口和设施负荷分配没有无意义波动。

低负荷的结论不应是“明显提高效率”，而应是“在共享设施未显著超载时保持稳定”。

### 6.4 高负荷场景：共享瓶颈缓解效果

目的：证明方法解决了核心问题。

应展示：

- 关键设施到达负荷压力下降；
- 排队持续时间、拥挤人时、尾部疏散时间下降；
- 线路到出口或线路到设施的分配更均衡；
- 若平均时间不占优，要诚实写成“尾部风险/瓶颈滞留改善，但平均效率存在权衡”。

### 6.5 机制解释：路径为什么变了

目的：证明效果不是偶然。

应展示：

- 哪些客流批次从原瓶颈设施转向其他设施；
- 转移发生时，原设施的预测到达负荷压力是否已经升高；
- 转移后，原设施实际队列是否减少；
- 新设施是否出现瓶颈转移。

### 6.6 敏感性分析：结论边界

目的：证明结果不是参数偶然性。

应围绕服务能力、密度阈值、需求规模和重路由阈值展开，不要做与核心机制无关的参数堆叠。

### 6.7 Pathfinder 对照：微观仿真一致性

目的：证明中观模型的拥堵趋势有外部合理性。

不能写成“Pathfinder 证明真实有效”。更严谨的写法是：

> Pathfinder 对照用于检验不同路径组织方案在微观行人仿真中是否呈现相近的拥堵区域、出口使用和尾部疏散趋势，从而为中观模型结论提供独立仿真参照。

## 7. 推荐题目与章节结构

更推荐的题目：

**多线地铁换乘站应急疏散中的共享设施到达负荷预判与路径组织优化**

这个题目比“到达时刻瓶颈预判”更清楚，因为“共享设施”和“到达负荷”直接对应本文模型与实验。

建议章节：

1. 引言：多线换乘站疏散中的共享设施服务能力竞争与路径分配滞后失效；
2. 相关研究：地铁站疏散仿真、动态路径组织、容量约束与排队建模；
3. 问题刻画：共享设施到达负荷超载的滞后识别机制；
4. 方法：共享设施到达负荷预判的路径组织模型；
5. 案例与实验设计：龙阳路站、低负荷/高负荷、基线、敏感性、Pathfinder；
6. 结果：问题诊断、机制验证、低负荷稳定性、高负荷瓶颈缓解、敏感性与 Pathfinder 对照；
7. 讨论：适用条件、参数来源、与既有方法关系、局限；
8. 结论。

## 8. 这一版的主线

最终可以压缩成一句话：

> 本文发现并刻画了高负荷多线地铁换乘站疏散中基于当前状态的路径分配对共享设施未来到达负荷超载识别滞后的问题，提出一种将已分配客流的承诺到达量、设施服务能力和预测等待时间纳入路径分配的疏散组织模型，并通过低负荷稳定性、高负荷瓶颈缓解、参数敏感性和 Pathfinder 微观仿真对照验证其有效性与适用边界。

这才是接近参考论文的逻辑：发现一个明确失效机制，把失效机制变量化，再让预测、优化、仿真和评价都围绕这个变量闭合。
